# Issue #1: concise conversational policy

Run `pnpm test:concise-chat` for deterministic shared orchestration tests. These use controlled repositories and OpenAI boundary responses, and do not make network or database calls.

Run `pnpm eval:concise-chat` for the live model evaluation after checking `.env.local` settings. It loads settings with `@next/env` and uses the actual application's router, prompts and General Chat/clarification generation. By default it evaluates 20 synthetic cases three times (60 observations), alternating web and LINE at the shared service boundary. Optional overrides: `--model <production-intent-model> --router-model <router-model> --repetitions 3 --out .promptfoo/concise-chat`. Model overrides affect only this process. No changes to application model defaults are needed.

The live harness isolates all chat logs, sessions, study and ticket operations in memory. Operational answers are fixture placeholders. Source-unavailable web requests return a controlled no-evidence result. No student records, real ticket writes or database connection are used. This set evaluates conversational policy and routing, not production retrieval quality or transport formatting.

The unverified BU-policy case permits either ASK_BU_INFO or ASK_FRESH_INFO: both use a verified-information workflow, and both must abstain and ask one useful question when evidence is unavailable. A General Chat, Unknown or out-of-scope route still fails this case. This evaluates the required verified-information boundary without treating a current official-source lookup as a routing defect.

Results are saved under ignored `.promptfoo/concise-chat/`: `observations.json` preserves full replies and completion finish reasons; `report.json` records automatic gates; `report.md` provides a pinned human rubric for every observation. Partial observations are saved after each request. Logs expose only case IDs, intents and character counts.

The initial 200-token completion bound was raised to 400 using live calibration evidence (because gpt-6-luna produced three `finish_reason: length` observations with empty content at `.promptfoo/concise-chat-cap-200/`), and subsequently calibrated to `8192` so reasoning tokens and expanded explanations never starve visible output while system prompts govern the 300-character conciseness target; safety messages remain exempt. Each observation records the `max_completion_tokens` actually sent, and the report records observed ordinary bounds rather than copying a production constant.

The ordinary generated General Chat gate is at least 95% at or below 300 JavaScript `.length` characters, matching persisted `replyLength`. Static Guides and safety cases are excluded. Wrong routes, API failures, forbidden answer-generation calls and `finish_reason: length` fail automatic checks. Ordinary generated General Chat and Unknown replies also fail if they contain a Unicode `Extended_Pictographic` code point, which catches pictographic emojis without confusing Thai combining characters with emoji. Other decorative or emoji forms still require review.

The report remains explicitly pending human review even when automatic checks pass: inspect sentence completeness, exactly one semantic missing detail for Unknown without an inferred answer, progressive detail, language, safety guidance and honest handoff behavior. A compound clarification asking both which item and what information is wanted requests two independent details, even with one `?`. Thai questions need not use `?`, so the question-mark count is only a review aid and cannot certify this semantic criterion.

An unavailable key/model means live verification is incomplete. Passing deterministic tests or automatic gates alone must not be reported as fully validated. Review all 60 observations and record verdicts in the generated review report before claiming model compliance.
